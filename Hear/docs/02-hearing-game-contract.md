# Hearing game contract

This is the most important implementation boundary.

## Measurement loop

Conceptually:

```text
session / trial engine
  -> decides trial parameters
  -> plays tone OR runs silent catch trial
  -> accepts tap/no-tap
  -> classifies outcome
  -> stores measurement result
  -> sends PRESENTATION outcome to active world
  -> waits until world is listening-safe again
  -> next trial
```

## Outcome model

Recommended conceptual model (adapt to the existing codebase rather than blindly copying):

```csharp
public enum TrialOutcome
{
    CorrectDetection,
    Miss,
    FalsePositive,
    CorrectRejection
}

public enum EarChannel
{
    Combined, // phone/computer speaker mode
    Left,
    Right
}
```

World presentation may receive an immutable context containing at least:

- classified outcome,
- ear channel,
- normalized session progress (0..1),
- world-safe presentation metadata if necessary.

It should **not** receive a callback that exposes stimulus onset for the purpose of visual presentation.

## Hard rules

1. A visual event must never reliably announce that a tone just started.
2. Ambient visual motion must be independent of stimulus timing.
3. A tap anywhere in the active response window is sufficient. Do not require aiming at a visual object.
4. Player dexterity must not determine audiometric success.
5. World feedback occurs only after classification.
6. The next listening window begins only when the world reports it has returned to a listening-safe state.
7. Misses and false positives are treated gently.
8. Catch trials must work in every world without requiring a visible fake target.

## Speaker vs headphones

### Speaker mode

- `EarChannel.Combined`.
- Do not claim ear-specific results.
- The game remains fully playable.

### Headphone mode

- Trials may target `Left` or `Right`.
- A world may use the ear information **after outcome classification** to lateralize the success event.
- Example: River Journey can paddle on the corresponding side; Tide Troubles can select a target on that side.
- Ear presentation is optional; not every world must use it.

## Session progress vs performance

Do not make completion of the world depend on hearing performance.

Separate:

- **SessionProgress:** how far the measurement session has advanced. This always reaches 1.0.
- **Performance presentation:** extra success events generated by correct detections.

A user who misses tones must still finish the scene/session. For example, River Journey may drift continuously with session progress, while correct detections add convincing paddle strokes and short acceleration impulses.
