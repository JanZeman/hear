# AGENT_BASE.md

> **Do not edit this file in your project.** It describes the documentation system itself and is
> intentionally project-agnostic. Project-specific rules, file lists, and topology belong in
> `AGENTS.md`. When the agent-base evolves upstream, replace this file wholesale.

Vendor-neutral, project-agnostic standard for organizing agent-facing documentation.

In an agent-driven workflow, Markdown is effectively a programming language - it defines how agents
behave, what they read, and which rules they follow. This document describes a reusable structure
for that Markdown so that any agent vendor - today's or tomorrow's - can work from the same files
as human contributors, without maintaining separate rulebooks per tool.

## Purpose

Use this document to define:

- how Markdown files are organized
- how AI agents consume and follow those files
- which files are canonical versus supporting
- how to avoid duplicate instructions
- how to keep the system portable across projects and agent vendors

The goal is simple: humans and agents should read the same source of truth, in the same order, with
the same conflict rules.

## Core Principles

### 1. Markdown is the control plane

Markdown is a practical default for agent-facing project governance because it is:

- easy for humans to read and edit
- easy for agents to parse
- diffable in git
- portable across tools
- stable over time

If a rule, workflow, or scope decision matters, it should exist in a Markdown file before it exists
in someone's memory.

### 2. One owner file per topic

Every important topic should have exactly one canonical owner file.

Examples of topic boundaries:

- agent and human behavior rules
- architecture rules
- environment setup
- branching model
- feature specifications
- skill procedures
- release or project-management tracking
- formatting and linting rules

All other files should link to that owner file rather than restating the same rule text.

### 3. Stable filenames beat clever filenames

Agents perform better when important files have predictable names and paths.

Examples of stable, reusable conventions:

- `AGENTS.md` for behavior and operating rules
- `README.md` for high-level project overview
- `.agents/roadmap/_ROADMAP_CATALOG.md` for roadmap (strategic overview, exit criteria, and execution steps)
- `.agents/roadmap/` for execution-level release steps
- `.agents/VENTURE.md` for Purpose, Vision, and Strategy
- `.agents/products/` for Products and Product-scoped Features
- `CONTRIBUTING.md` for the human-facing contribution policy, never agent instructions
- `.agents/standards/formatting.md` for all formatting and linting rules
- `.agents/standards/` for topic-specific standards
- `.agents/skills/` for repeatable procedures
- `.agents/workflows/` for team workflows

Choose names that are obvious enough that a new human or a new agent can guess them correctly.

### 4. Numbering where sequence matters, plain names where it doesn't

Numbering is not a blanket convention - it is a deliberate choice for categories where
discovery order or dependency chains carry real meaning:

- **Numbered** (`NNN-kebab-name.md`, starting at `001`, numbers permanent - never reused or
  shuffled): Features inside a Product, `.agents/goals/`, `.agents/roadmap/`. These have a real
  before/after relationship worth preserving. Goal identifiers use that same prefix (`NNN`);
  their key results are `NNN-KRN`, with no `O` prefix.
- **Plain** (`kebab-name.md`, no numeric prefix): `.agents/standards/`, `.agents/skills/`,
  `.agents/workflows/`. These are flat catalogs of named things with no inherent order
  between entries - a stable descriptive name is as permanent an identifier as a number, and
  reads far better in conversation and cross-references. It also avoids a real failure mode:
  a small shared numeric sequence collides the moment two independent parties (a project and
  agent-base) both assign numbers into it, whereas a descriptive name collision is rare and,
  when it happens, actually means something.
- Each directory still has a `_*_CATALOG.md` (canonical index) and `_*_TEMPLATE.md`
  (structure skeleton) regardless of which convention it uses.

Whichever kind, cross-references stay stable across time and tools because the identifier
(number or name) is never reused or renamed once assigned.

### 5. Precedence must be explicit

Do not assume agents or humans will infer which file wins during conflicts.

A good system states precedence clearly, for example:

1. Global behavior contract (`AGENTS.md`)
2. Topic-specific canonical docs
3. Tool-specific adapter files

Without this, the same repository slowly accumulates multiple "truths."

### 5a. Agent-base rule ownership is namespaced

Every default injected inside `AGENTS.md`'s managed `AGENT-BASE-RULES` block uses an `AB-*`
ID. Unprefixed IDs belong to the downstream project, even when the suffix matches an
agent-base default. This keeps independently designed project rules from colliding with the
base contract and lets overrides name their target unambiguously.

Compatibility: releases through v0.0.96 injected the same defaults without `AB-`. Historical
references from that period map suffix-for-suffix (`GIT-001` -> `AB-GIT-001`, and so on) only
when the source clearly meant the old agent-base default. They are documentation aliases, not
active rule declarations; new content and overrides use `AB-*`. Never mechanically rename an
unprefixed downstream rule.

### 6. Roadmap alignment is an agent-base-level contract

Every task an agent starts must be justified against the product roadmap before any planning or
code work. The agent-base enforces this via two cooperating layers:

- Short `Every Change` and `Task Start` sections are injected into every vendor adapter (Warp,
  Claude Code, Copilot) from `.agents/hooks.md`. They require the complete `AGENTS.md` contract
  and highlight Venture Context, Goals, Roadmap, and authority boundaries without copying rules.
- The canonical alignment rule lives in `AGENTS.md` as `AB-ROADMAP-001 [P0]`, so humans reviewing
  PRs can cite it and Codex (which reads `AGENTS.md` natively) picks it up without an adapter.
- `AB-ROADMAP-002 [P0]` requires agents to close completed in-scope roadmap work proactively in
  the same turn, report their evidence and any hesitation, and invite correction. Outside a
  verified direct Agent Base update, the human accepts by reviewing and committing; ordinary
  checkpoints do not imply a push. `apply-agent-base.sh` updates the managed
  `AGENT-BASE-RULES` block in `AGENTS.md` (also carrying `AB-GIT-001`, `AB-GIT-002`,
  `AB-SYNC-001`, `AB-HUMAN-001`, `AB-DESIGN-001`, `AB-DOC-005`, and `AB-SAFE-001` -- every generic,
  non-project-specific rule), migrating older unmarked or differently-named blocks when needed,
  so every downstream repo receives the current canonical rule text even when the rest of that
  customize-once file has diverged. Drift detection excludes these automatically refreshed
  ranges and reports only upstream changes in project-owned portions of customize-once files.
  Vendor adapters point to `AB-ROADMAP-001` and `AB-ROADMAP-002` in `AGENTS.md`; they do not
  duplicate either rule. The same managed-range mechanism injects the autonomy diagnostic into
  existing customized `agent-base-guard.sh` files.

This is intentionally agent-base-level, not project-specific: the agent-base’s goal is portable,
vendor-neutral agent behavior, and roadmap alignment is the minimum coordination needed for
any agent-driven workflow to stay on track.

### 7. Adapters should stay thin

If you support multiple agent tools, do not maintain a separate policy book for each one.

Instead:

- keep the real rules in one canonical file
- let tool-specific files be adapters
- use adapters only for tool syntax, wiring, or short compatibility notes

This keeps the system maintainable when agent vendors change.

## Venture Operating Model

The repository itself is one independently managed **Venture**. `.agents/` is its descriptive and
operating layer; it does not need a redundant `venture/` container. The canonical structure is:

```text
Venture
├── Departments
├── Feedback
├── Goals
├── Products
│   └── Product
│       └── Features
├── Resources
├── Roadmap
├── Skills
├── Standards
└── Workflows
```

Purpose, Vision, and Strategy live in `.agents/VENTURE.md`; Goals retain their existing canonical
directory. A generated bounded summary in `AGENTS.md` is only a fallback. At session start,
`scripts/venture.py context` composes the full context and fails closed before substantive work if
either source is missing or unfilled.

An undefined context first invokes `.agents/agent-base/skills/venture-discovery/SKILL.md`. The
agent elicits intent from the human directing the Venture before drafting any content; repository
evidence informs follow-up questions but never substitutes for human motives, constraints, or
Goals. Existing approved context is not routinely reopened.

Departments are responsibility lenses, not simulated employees or mandatory folders. The generic
catalogue under `.agents/agent-base/departments/` defines Management, UX, Engineering, Quality,
Security, Safety, Marketing, Sales, Support, Finance, Legal, HR, and Operations. Route each
substantive phase to one Lead Department and consult only materially affected others. Create a
Venture-specific `.agents/departments/<name>.md` overlay only when durable local knowledge exists;
promote that file to a directory only when several genuine artifacts justify it.

Products are anything of value the Venture creates or provides, including services and internal
Products. Features are Product-scoped capabilities or outcomes, never a parallel root category.
Feedback is a Venture-wide intake and deduplication registry because classification may involve
several Products or Departments. Resources records only durable, significant assets or dependencies
whose visibility improves decisions, continuity, risk, or operation. Activate these Categories only
when they contain real information; framework creation templates live under
`.agents/agent-base/templates/` so a new Venture does not start with empty bureaucracy.

The detailed boundaries, anti-bureaucracy test, routing rules, and wiki authority model live in
`.agents/agent-base/standards/venture-operating-model.md`.

### Operator-local wiki mapping

The optional wiki registry lives at
`${XDG_CONFIG_HOME:-$HOME/.config}/agent-base/wikis.json`. It maps any local Venture, including
Agent Base itself, without making that repository a downstream fleet member:

```json
{
  "wikis": [
    {
      "path": "/absolute/local/repository",
      "connector": "operator-connector-id",
      "root": "en/ventures/venture-slug",
      "host": "wiki.example.com"
    }
  ],
  "visibility_policies": {
    "wiki.example.com": {"default": "public", "private_path_segments": ["internal"]}
  }
}
```

On a dedicated host, `root` is normally `en/internal`; on a shared host it is normally
`en/ventures/<venture-slug>`. The connector selects the wiki connection, while `host` and
`visibility_policies` classify privacy by exact host and complete path segment. Run
`python3 scripts/venture.py --root . wiki-visibility` before a mapped wiki write; see
`.agents/agent-base/standards/wiki-visibility.md` for unknown or arbitrary targets. This
configuration is local operational context, not Venture content: never copy its concrete values,
absolute paths, host URLs, or credentials into the repository.

For transition compatibility, `venture.py` reads nested `wiki` objects from the operator's legacy
`downstreams.json` only when `wikis.json` does not exist. This fallback is read-only; fleet
eligibility remains determined independently by the entries in `downstreams.json`, which should
contain only actual clients.

## Recommended File Topology

This structure is intentionally generic and reusable:

- `AGENTS.md`
  - Canonical operating contract for human contributors and coding agents
  - Includes precedence, safety rules, workflow rules, and the source-of-truth map
- `README.md`
  - High-level project overview, roadmap, orientation, and entry points
- `CONTRIBUTING.md`
  - Human-facing contribution policy; agents are not required to read it
  - Seeded once with a private, single-maintainer default; first seed reports repository
    visibility when available and always asks a human to review it
- `AGENT_BASE.md`
  - Meta description of the documentation and agent-instruction system itself

Recommended agent-specific folders:

- `.agents/standards/`
  - Topic-specific standards that agents discover via the source-of-truth map in `AGENTS.md`
  - Plain `kebab-name.md`, no numeric prefix (see "Numbering" above). Examples:
    `architecture.md`, `development-workflow.md`, `formatting.md`
  - Each directory includes `_STANDARDS_CATALOG.md` (index) and `_STANDARDS_TEMPLATE.md` (skeleton)
  - Rule: if no tool or convention requires a file at the repo root, it belongs here
  - Agent-base's own canonical reference docs (not project content) live separately in
    `.agents/agent-base/standards/`, kept in sync automatically - never mixed into this
    project-owned directory
- `.agents/products/` (created only when the Venture has a real Product)
  - `_PRODUCTS_CATALOG.md` is the canonical list of external and explicitly marked internal Products
  - One folder per Product, containing `PRODUCT.md` and optional `features/`
  - Product Features are numbered (`NNN-kebab-name.md`) within that Product and indexed by its
    `_FEATURE_CATALOG.md`
- `.agents/departments/`, `.agents/feedback/`, `.agents/resources/` (created on evidence)
  - Venture-specific Department knowledge, classified feedback, and significant Resources
  - Creation skeletons live under `.agents/agent-base/templates/`; no empty Category is seeded
- `.agents/workflows/`
  - Team workflows: review, release, feature delivery, debugging playbooks
  - Workflows describe *what the team does*; skills describe *how an agent executes a step*
  - Plain `kebab-name.md`, no numeric prefix
  - Includes `_WORKFLOW_CATALOG.md` (index) and `_WORKFLOW_TEMPLATE.md` (skeleton)
- `.agents/skills/`
  - One folder per skill (`skill-name/SKILL.md`, no numeric prefix), following the [Agent Skills](https://agentskills.io/specification) open format
  - Includes `_SKILLS_CATALOG.md` (index) and `_SKILLS_TEMPLATE.md` (creation guide)
- `.agents/agent-base/skills/`
  - Generic agent-base-owned skills, kept in sync automatically and never customized by the
    downstream project
  - Separate from the project's `.agents/skills/` namespace for the same ownership reason as
    agent-base-owned standards
- `.agents/roadmap/`
  - One doc per item (`NNN-kebab-name.md`) for its entire life, each with status, definition
    of done, notes - an idea, a committed step, and an archived item are the same kind of
    thing at different points in one lifecycle, tracked by `Status` alone
  - Includes `_ROADMAP_CATALOG.md` (execution index) and `_ROADMAP_TEMPLATE.md` (skeleton).
    No separate ideas file or archive file: an idea is `Status: Idea` in the same file/row
    shape as everything else, kept deliberately light until promoted to `Status: Open`
  - `_ROADMAP_CATALOG.md` is the single roadmap document: strategic overview, exit criteria, and daily work queue
- `agent-base-guard.sh` (repo root)
  - Agent documentation integrity guard - lives at root for visibility and CI access
- `.agents/agent-base/banner.txt`
  - Canonical session wordmark; the guard and first-response rule render its `<version>` field
    from `AGENT_BASE_VERSION`
- `.agents/hooks.md`
  - Session-start commands and shared adapter triggers, including the first-response banner
  - Kept in sync with the agent-base; `apply-agent-base.sh` injects these into vendor adapters
- `scripts/human-interruptions.py`
  - Optional machine-wide, content-free request telemetry for Codex and Claude
  - Sync distributes it but never installs or enables global hooks; see
    `.agents/agent-base/standards/human-interruptions.md`
- `scripts/agent-autonomy.py`
  - Four-vendor sandbox/automatic-review diagnostics and explicit machine-wide lifecycle
  - The guard inspects actual machine, project, and VS Code state
  - Root `vendor.sh` audits, requests explicit consent, backs up changed settings, and prints a
    validated restore command before the helper applies Agent Base-owned values
  - See `.agents/agent-base/standards/agent-autonomy.md`
- `vendor.sh` (repo root)
  - Consent-gated entry point over `scripts/agent-autonomy.py`; keep in sync across clients
- `scripts/session-snapshots.py`
  - Validates explicit `Continues` lineages and retains their newest two handoff snapshots
  - Refuses ambiguous or unsafe deletion; see `.agents/agent-base/standards/session-continuity.md`
- `scripts/worktree-consolidate.sh` and root `worktrees.sh`
  - The keep-in-sync engine validates and consolidates only project-declared worktree slots; with
    `--repo-id CODE` it discovers `<CODE><N>` slots, checks the main worktree folder is `<CODE>`,
    and merges their `_<code><N>` branches
  - The customize-once wrapper declares nothing itself: it reads `stable_branch` and `repo_id`
    from `development-workflow.md`; using it does not expand agent Git authority beyond the one
    narrow, one-way `--to-slots-only` case a verified fleet update runs (`AB-GIT-001`, git.md)
- `.claude/`, `WARP.md`, `.github/copilot-instructions.md`, or similar
  - Thin tool adapters - also carry injected agent-base hooks between `AGENT-BASE-HOOKS` markers

## Catalog and Template Pattern

Artifact collections use this two-file pattern where a catalog is useful:

- `_*_CATALOG.md` - the canonical index for that category (Products, Product Features, feedback,
  Resources, standards, skills,
  workflows, roadmap). This is the single source of truth for what exists.
- `_*_TEMPLATE.md` - the reusable doc skeleton for creating new entries.

This pattern keeps each category self-documenting: an agent or human entering a directory can
always find the index and the template without guessing.

## Product and Feature Documentation Structure

A Product owns its Features. Feature docs work best when they are:

- isolated by feature
- named and numbered predictably (`NNN-kebab-name.md`)
- written purpose-first (what and why before how)
- precise enough for implementation

The feature template includes user-facing sections (user promise, JTBD, user flows, trust and
privacy expectations) before implementation sections (architecture mapping, testing strategy).
This ensures features are defined from the user's perspective first.

### Canonical rule for feature lists

The feature list should have one owner file.

Best practice:

- use `.agents/products/_PRODUCTS_CATALOG.md` as the canonical Product list
- use each Product's `features/_FEATURE_CATALOG.md` as its canonical feature index
- let `README.md` link to that catalog
- avoid repeating the full feature table in multiple places

Short summaries elsewhere are fine. Duplicate full lists are not.

## Refactorings Are Roadmap Steps

There is no dedicated `refactorings/` concept. Architectural refactoring work is tracked in
`.agents/roadmap/` like any other release step, with the word `refactoring` in the step's
filename (e.g. `007-refactoring-data-layer.md`). This keeps the number of top-level concepts
small and ensures refactoring work is prioritized against the same roadmap as every other
step.

When authoring a refactoring step, still capture: the problem, options considered, the
chosen option and rationale, key findings, and implementation notes. The roadmap step
template has room for this in its `Notes` section; expand the step doc as needed.

## How Agents Use This System

Agents usually work best when they can discover context progressively:

1. Read the global behavior contract.
2. Read the topic-specific canonical doc.
3. Read the exact feature or skill doc relevant to the task.
4. Ignore unrelated files unless blocked.

This keeps context smaller and makes behavior more predictable.

The documentation system should therefore be optimized for:

- discovery by filename
- predictable cross-links
- small, local scopes
- minimal duplication

## Agent Types: Current and Future

This structure is designed to support multiple agent styles, not one specific vendor.

Common agent categories:

- terminal-based coding agents
- IDE-integrated code assistants
- chat-based planning or review agents
- CI or bot-style automated reviewers
- future custom internal agents

Examples of agent vendors or products can change over time. The documentation system should not
depend on any single vendor name to remain valid.

### Current practical pattern

In most teams, one or more agents are used natively while others require adapter files.

A robust rule is:

- if an agent can read `AGENTS.md` directly, prefer that
- if an agent needs a tool-specific instruction file, point it back to the canonical docs

That makes adding a new agent cheap:

- add a thin adapter
- do not rewrite the rules

## Skills and Repeatable Workflows

Not every task deserves a new file. A skill is useful when a workflow:

- has at least a few stable steps
- is likely to recur
- benefits from consistent sequencing

Good skill candidates:

- describe a feature
- implement a feature
- review a change
- prepare a release
- create a migration plan

### Agent Skills format

Skills follow the [Agent Skills](https://agentskills.io/specification) open format. Each skill
is a folder containing a `SKILL.md` with YAML frontmatter and Markdown instructions:

```
.agents/skills/skill-name/
  SKILL.md        # Required: frontmatter (name, description) + instructions
  references/     # Optional: detailed reference docs
  scripts/        # Optional: executable code
  assets/         # Optional: templates, schemas
```

Agents use progressive disclosure:

1. At startup, only `name` and `description` are loaded (all skills)
2. When a task matches, the full `SKILL.md` body is read
3. Referenced files are loaded on demand

This means skills are portable across any agent that supports the spec - no vendor-specific
wrappers needed.

See `_SKILLS_TEMPLATE.md` for the full creation guide.

Skills should complement canonical docs, not replace them.

## Why This Markdown Structure Works

This structure is effective because it separates concerns cleanly:

- policy lives in one place
- specs live near their subject
- procedures live as skills
- adapters stay thin
- indexes summarize without owning the underlying truth

That combination helps with:

- easier onboarding for humans
- lower confusion for agents
- less drift between tools
- better reviewability in git
- safer long-term maintenance

## Change Protocol

When changing documentation in an agent-enabled repository:

1. Update the canonical owner file first.
2. Update only the directly affected supporting files.
3. Replace duplicated text with links where possible.
4. Run the repository's formatting and lint scripts (see `.agents/standards/formatting.md`).
5. Treat broken cross-links or duplicate ownership as real defects.

If the change affects behavior rules, update the behavior contract before updating adapters.

## Anti-Patterns to Avoid

Avoid these common failures:

- multiple files claiming to be the source of truth for the same topic
- copying the same rules into every tool adapter
- keeping a feature list in several full copies
- naming files in ways that humans understand only after tribal explanation
- writing docs only for humans and assuming agents will "figure it out"
- writing docs only for agents and making them unpleasant for humans
- scattering formatting rules across multiple files instead of owning them in one place

The right target is shared readability.

## Improvement Ideas

This system can be strengthened further in any future project.

### 1. Add a machine-readable manifest

In addition to Markdown, a small manifest file can define:

- canonical docs by topic
- doc precedence
- feature ownership
- validation rules

Use this only as a supplement. Markdown should remain the human-readable source.

### 2. Auto-check duplicate ownership

Add a script that verifies:

- each topic has one canonical owner
- adapters do not contain forbidden duplicated rule text
- indexes point only to real files

This prevents slow documentation drift.

### 3. Generate indexes instead of hand-maintaining them

Feature catalogs, skill lists, and doc maps can be generated from filenames and front matter.

This reduces manual duplication while keeping human-facing Markdown as the output.

### 4. Add lightweight front matter where useful

Optional front matter can help tools and agents understand:

- file purpose
- owner topic
- update priority
- status

Use it only if it remains simple and readable.

### 5. Add relationship diagrams

A small doc graph can help new contributors understand:

- which files are canonical
- which files are indexes
- which files are adapters
- which files are templates

This is especially helpful as the doc system grows.

### 6. Add periodic doc-audit procedures

Useful recurring audits include:

- duplicate-rule audits
- stale-link audits
- feature-catalog completeness audits
- adapter-thinness audits

These keep the documentation system healthy over time.

## Practical Reuse Rule

A new project should be able to copy this file and reuse the model directly if it keeps the same
basic conventions:

- one canonical behavior contract
- one owner file per topic
- one canonical feature index
- numbering where sequence matters (`NNN-kebab-name.md`), plain names elsewhere (see
  "Numbering" above)
- catalog + template files in every `.agents/` subdirectory
- Product-scoped feature docs in predictable folders
- skills in a predictable folder (vendor-neutral + tool wrappers)
- thin agent adapters
- one formatting standards file for all formatting rules

That is the real design goal: portability without depending on one product, one codebase, or one AI
vendor.

### Keeping in sync with the agent-base

The recommended approach is to add `agent-base` as a git submodule at `_sub/agent-base/`.
Running `bash _sub/agent-base/apply-agent-base.sh` copies keep-in-sync files (vendor adapters,
lint config, markdown linting script, this file) while leaving project-customized files untouched.
This makes agent-base updates a two-step operation: bump the submodule reference, run the apply script.

By default the apply script fetches upstream first and follows it if agent-base has moved on,
which is what an ordinary sync wants. Pass `--no-fetch` to apply exactly the commit that is
checked out instead. Use it whenever a specific release has been verified and frozen, so the
run cannot silently substitute a newer, unverified one. Either way the script reports the
agent-base commit it applied.

A standalone mode is also supported for projects that prefer not to use submodules.
